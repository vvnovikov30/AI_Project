# Единый технический бриф по требованиям к архитектуре тестирования критического ETL реконсилейшна ПСД

Настоящий документ определяет архитектурные требования, методологический комплекс и стандарты верификации детерминированного ETL-конвейера, выполняющего автоматизированный аудит и взаимную сверку (reconciliation) проектно-сметной документации (ПСД) в изолированном On-Premise / Air-Gapped контуре.

---

## 1. Фундаментальные принципы и политики верификации

### 1.1. Zero Float Policy (Тотальный запрет типа `float`)
* **Причина:** Использование аппаратного типа `float` стандарта IEEE 754 приводит к накоплению аномалий округления (копеечные расхождения на сметных объемах в миллионы рублей заблокируют прохождение государственной экспертизы).
* **Требование:** Все объемные и финансовые вычисления (`quantity`, `unit_multiplier`, `base_price`, `total_cost`, `delta`) производятся исключительно через класс `decimal.Decimal`.
* **Хранение в БД:** В буферных таблицах SQLite данные сохраняются строго в текстовом типе (`TEXT`), исключающем автоматическое приведение типов с плавающей точкой со стороны СУБД.
* **Статический барьер:**
  1. **`ast-grep` (sg):** Блокировка вызовов `float()`, синтаксиса `-> float`, объявлений `: float` и литералов с точкой в расчетном ядре.
  2. **`ast.NodeVisitor`:** Пользовательский AST-анализатор в `pre-commit`, проверяющий отсутствие float-литералов (например, `0.05`).
  3. **`pytest-archon`:** Архитектурный контроль изоляции расчетного ядра от сторонних неточных пакетов (`numpy`, `pandas`, `math`, `scipy`).

### 1.2. Гарантия Аудиторского Следа (Audit Trail Invariance)
* Каждая запись обязана содержать объект `CellPointer` (физический указатель источника: тип документа, имя файла, версия, листы/страницы, индексы строк и колонок, адрес ячейки `C24`).
* **Инвариант:** Пространственные индексы `CellPointer` не могут модифицироваться, сбрасываться или искажаться на всех этапах нормализации и расчета.

## 2. Четырехуровневая пирамида тестирования (Testing Pyramid)

Для работы компактной инженерной команды (2–5 человек) время локального прогона тестов ограничено **90–120 секундами**, чтобы не снижать скорость разработки.

```
                  ┌─────────────────────────────────────────┐
                  │       L4: Heavy Mutation & Snapshots    │  5–15 мин (CI / Release)
                  │   pytest-gremlins, syrupy Golden Masters │
                  ├─────────────────────────────────────────┤
                  │     L3: Property-Based & Metamorphic    │  30–60 сек
                  │      Hypothesis, rapidfuzz, MR-1..MR-5  │
                  ├─────────────────────────────────────────┤
                  │          L2: Fast Unit & Gates          │  10–25 сек
                  │  pytest, Pydantic v2, in-memory SQLite  │
                  ├─────────────────────────────────────────┤
                  │         L1: Static Gate (Pre-commit)    │  < 2 сек
                  │  ast-grep, ruff, mypy, ast.NodeVisitor   │
                  └─────────────────────────────────────────┘
```

### 2.1. L1: Static Gate (Pre-commit)
* **Назначение:** Мгновенный контроль стиля, типов и соблюдения Zero Float Policy.
* **Инструменты:** `ast-grep`, `ruff`, `mypy`, `ast.NodeVisitor`.
* **Время исполнения:** `< 2 секунд` (запускается автоматически при каждом git commit).

### 2.2. L2: Fast Unit & Gates (Модульное тестирование)
* **Назначение:** Изолированная проверка логических шлюзов, правил нормализации единиц измерения ОКЕИ, формул и структур Pydantic v2.
* **База данных:** Использование `in-memory SQLite` с настраиваемыми URI (`file:memdb_{worker_id}?mode=memory&cache=shared`) для параллельного запуска через `pytest-xdist`.
* **Время исполнения:** `10–25 секунд`.

### 2.3. L3: Property-Based & Metamorphic Testing
* **Property-Based Testing (Hypothesis):**
  * **Инвариант идемпотентности нормализации:** $f(f(x)) = f(x)$ для функций лексической очистки наименований и нормализации строк.
  * **Инвариант обратимости сериализации (Round-trip):** Сохранение битовой идентичности Decimal и структуры `CellPointer` при схеме `Pydantic v2 -> SQLite (TEXT) -> Pydantic v2`.
  * **Инвариант аддитивности:** Сумма нормативных стоимостей ресурсов с учетом отходов ($K_{\text{отход}}$) сохраняет формульную целостность.
* **Метаморфическое тестирование (Metamorphic Testing, MT):**
  * **MR-1 (Симметрия сходства):** $S(A, B) = S(B, A)$.
  * **MR-2 (Токенизационная инвариантность):** Перестановка слов при сохранении технических характеристик не уменьшает показатель сходства ниже $\varepsilon$-порога (например, «Кабель ВВГнг-LS 3х1.5» vs «ВВГнг-LS кабель 3х1.5»).
  * **MR-3 (Устойчивость к нейтральному контексту):** Внедрение стоп-слов («по ГОСТ», «в сборе») не меняет ранжирование топ-$K$ кандидатов.
  * **MR-4 (Разрушение шлюза размерности — Dimensional Lock):** Любая модификация калибра (изменение сечения кабеля с 3х1.5 на 5х6 или диаметра трубы с 108х4 на 159х4.5) мгновенно сбрасывает $\mathbb{I}_{\text{dim}} = 0.0$ и итоговый скор $S_{\text{total}} = 0.0$.
  * **MR-5 (Разрушение шлюза единиц — Unit Gating):** Попытка матчинга физически несовместимых величин (м² vs м³) обнуляет $\mathbb{I}_{\text{unit}} = 0.0$.
* **Время исполнения:** `30–60 секунд`.

### 2.4. L4: Snapshot Testing & Mutation Analysis (CI/Release)
* **Snapshot-тестирование (Syrupy + Golden Masters):**
  * **Назначение:** Регрессионный контроль парсинга нестабильных табличных топологий (объединенные ячейки `merged_cells` в Excel по Приказу № 421/пр, сканы и векторные таблицы PDF по ГОСТ 21.110-2013).
  * **Канонизация:** Использование `AmberSnapshotExtension` для удаления абсолютных путей и временных меток из снимков.
  * **Десенситизация:** Псевдонимизация названий коммерческих организаций и масштабирование цен при сохранении формульной целостности смет.
* **Мутационный анализ (pytest-gremlins / mutmut):**
  * **Ограничение области:** Мутируются строго ключевые модули ядра (`gates.py`, `scoring.py`, `anomalies.py`).
  * **Проверяемые мутации:** Выживаемость операторов сравнения (`==` $\rightarrow$ `!=`, `and` $\rightarrow$ `or`), инверсия деления на умножение в детекторах кратности ($10\times, 100\times, 1000\times$) и замена `Decimal` на `float`.
* **Время исполнения:** `5–15 минут` (фоновый CI прогон).

## 3. Метрики эффективности и качества ранжирования

Тестовый контур обязан валидировать как алгоритмическую точность, так и экономическую полезность системы:

| Группа метрик | Метрика | Формула / Описание | Пороговое значение |
| :--- | :--- | :--- | :--- |
| **Качество ранжирования** | **Precision@K** | Доля корректных эталонных связок среди первых $K$ предложенных кандидатов | $P@1 \ge 0.90$, $P@3 \ge 0.98$ |
| | **MRR** | Mean Reciprocal Rank (средний обратный ранг эталонной строки) | $MRR \ge 0.92$ |
| | **NDCG@K** | Normalized Discounted Cumulative Gain (учитывает порядок кандидатов) | $NDCG@3 \ge 0.95$ |
| **Качество детекции** | **Collision Recall Rate (CRR)** | Процент выявленных реальных сметных ошибок, подтвержденных экспертизой | $CRR \ge 95\%$ |
| **Экономический риск** | **Budget Risk Value ($\Delta B$)** | Суммарный предотвращенный перерасход $\Delta B = \sum (V_{\text{est}} - V_{\text{spec}}) \cdot C_{\text{unit}}$ | Вычисления строго в `Decimal` |

## 4. Конфигурационные регламенты и профили Hypothesis

Для обеспечения высокой скорости прогона на локальных компьютерах разработчиков в `conftest.py` настраиваются динамические профили `Hypothesis`:

```python
# conftest.py
import os
from hypothesis import Phase, settings

# Профиль для быстрой локальной разработки
settings.register_profile(
    "dev",
    max_examples=25,
    deadline=400,
    phases=[Phase.explicit, Phase.reuse, Phase.generate],
)

# Профиль для глубокой проверки на сервере интеграции CI
settings.register_profile(
    "ci",
    max_examples=300,
    deadline=None,
    phases=[
        Phase.explicit,
        Phase.reuse,
        Phase.generate,
        Phase.target,
        Phase.shrink,
    ],
)

selected_profile = os.getenv("HYPOTHESIS_PROFILE", "dev")
settings.load_profile(selected_profile)
```
