## 2. Назначение и границы системы

### 2.1. Цель разработки
Автоматизация выявления пространственно-количественных, номенклатурных и нормативных расхождений между проектной частью (ведомости объемов работ — ВОР, спецификации чертежей) и сметной частью (локальные сметные расчеты — ЛСР) объектов капитального строительства, с углубленным анализом внутренних инженерных систем (электроснабжение, слаботочные системы). 

### 2.2. Границы ответственности модуля
* **Входит в скоуп:**
  * Парсинг табличных форм ЛСР по Методике 421/пр (форматы `.xlsx`, `.xls`).
  * Извлечение проектных спецификаций из табличных и текстовых форматов (`.xlsx`, `.pdf`).
  * Канонизация строительных наименований и единиц измерения с сохранением топологической ссылки на ячейку (`CellPointer`).
  * Сопоставление кабельной продукции с учетом жильности, сечения и типа изоляции.


  * Парсинг табличных форм ЛСР по Методике 421/пр (форматы `.xlsx`, `.xls`) и проектных спецификаций (`.xlsx`, `.pdf`).

  * Блокирующая валидация физических размерностей (Unit Gating) и геометрических габаритов (Diameter/Thickness Lock).
    * Расчет коэффициента подобия (semantic/fuzzy similarity) между строками спецификаций и смет.
  * Детекция задвоения ресурсов и разделение материалов, учтенных внутри комплексных расценок (гофротруба, крепеж).
  * Формирование детерминированного отчета о коллизиях и финансовом риске (Budget Risk Value).

* **Не входит в скоуп:**
  * Электротехнические расчеты (токи короткого замыкания). Прямой парсинг бинарных файлов CAD/BIM (`.dwg`, `.ifc`). Пересчет индексов.

## 3. Архитектура 5-фазного конвейера ETL

[Фаза 1: Ingestion & Topology Extraction]
  ├── openpyxl (extract_sheet_rows_unmerged) -> ЛСР (421/пр) и ВОР (Excel)
  └── pdfplumber / openpyxl -> Спецификации (СПДС), спецификации оборудования и кабельные журналы (PDF / Excel)
                            │
                            ▼
[Фаза 2: Normalization & Canonicalization]
  ├── Топологическая привязка (CellPointer)
  ├── Лексическая чистка (ABBREVIATIONS_MAP, общестроительные и MEP стоп-слова)
  └── Канонизация размерностей в Decimal (м2, м3, т, м, км, шт, компл)
                            │
                            ▼
    [Фаза 3: Intermediate Checkpoint (SQLite)]
      └── Таблица audit_staging (Human-in-the-Loop аудит промежуточных распарсенных строк)
                            │
                            ▼
    [Фаза 4: Gated Hybrid Matching Engine]
      ├── Unit Gating (I_unit) -> запрет сравнения несовместимых размерностей
      ├── Dimensional Lock (I_dim) -> проверка сечений и габаритов
      └── Вычисление скоринга: w1*Code + w2*Fuzzy + w3*Context
                            │
                            ▼
    [Фаза 5: Collision Analysis & Reporting]
      ├── Детекция скрытых сдвигов кратности (Multiplier Shift 10x, 100x, 1000x)
      ├── Анализ запаса кабеля (Cable Slack Tolerance)
      └── Экспорт DiscrepancyReportItem в JSON / Excel

## 4. Схемы данных (Pydantic v2 Models)

```python
from decimal import Decimal
from typing import Annotated, Literal, Optional
from pydantic import BaseModel, ConfigDict, Field, field_validator, model_validator


class CellPointer(BaseModel):
    """Топологический указатель источника данных в первичном документе (Audit Trail)."""
    model_config = ConfigDict(frozen=True)

    doc_type: Literal["SPECIFICATION", "VOR", "LSR", "SSR"] = Field(
        ..., description="Тип исходного документа"
    )
    file_name: str = Field(..., description="Физическое имя файла на диске")
    doc_version: str = Field(
        default="v1.0", description="Метка версии документа (например, 'Изм.2', 'Утвержденный')"
    )
    sheet_name: str = Field(..., description="Имя вкладки Excel или номер страницы PDF")
    row_idx: int = Field(..., ge=1, description="Индекс строки (1-based)")
    col_letter: str = Field(..., description="Буквенный индекс колонки (например, 'C')")
    coordinate: str = Field(..., description="Полный буквенно-цифровой адрес (например, 'C24')")


class AuditLineItem(BaseModel):
    """Канонизированная строка строительной ведомости/сметы."""
    model_config = ConfigDict(arbitrary_types_allowed=True)

    pointer: CellPointer
    item_code: Optional[str] = Field(
        None, description="Шифр расценки (ФЕР, ГЭСН, ТСН, ТЦ) или артикул материала"
    )
    raw_title: str = Field(..., min_length=1, description="Исходный текст из документа")
    clean_title: str = Field(..., description="Нормализованное наименование (без стоп-слов и сокращений)")
    
    # Объемы и цены строго через Decimal
    quantity: Decimal = Field(..., description="Физический объем")
    raw_unit: str = Field(..., description="Исходная единица измерения (например, '100 м2')")
    canonical_unit: str = Field(..., description="Базовая физическая размерность (например, 'м2')")
    unit_multiplier: Decimal = Field(
        default=Decimal("1.0"),
        description="Коэффициент приведения к базовой единице (для '100 м2' -> 100.0)"
    )
    base_price: Optional[Decimal] = Field(
        None, description="Прямые затраты / сметная цена за единицу"
    )

    @field_validator("quantity", "unit_multiplier", "base_price", mode="before")
    @classmethod
    def parse_strict_decimal(cls, value: object) -> Optional[Decimal]:
        """Защита от неявного приведения через float. Принимает int, str или Decimal."""
        if value is None:
            return None
        if isinstance(value, float):
            raise TypeError(
                f"Недопустимо использовать тип float ({value}) для объемов/цен сметы. "
                "Преобразуйте значение в str перед валидацией."
            )
        if isinstance(value, (int, str)):
            sanitized = str(value).replace(" ", "").replace(",", ".").strip()
            return Decimal(sanitized)
        if isinstance(value, Decimal):
            return value
        raise ValueError(f"Невозможно привести {value} к Decimal.")


class DiscrepancyReportItem(BaseModel):
    """Модель зафиксированной стоимостной или объемной коллизии."""
    model_config = ConfigDict(arbitrary_types_allowed=True)

    collision_type: Literal[
        "VOLUME_OVERRUN",      # Превышение объема сметы относительно спецификации
        "MULTIPLIER_ERROR",    # Ошибка кратности (забытое деление на 10, 100, 1000)
        "INCOMPATIBLE_UNITS",  # Конфликт физических размерностей (м2 vs м3)
        "DUPLICATE_RESOURCE"   # Задвоение ресурса в смете
    ]
    severity: Literal["CRITICAL", "WARNING", "INFO"]
    spec_pointer: CellPointer
    estimate_pointer: CellPointer
    
    spec_qty: Decimal
    normalized_est_qty: Decimal
    delta: Decimal = Field(..., description="Абсолютное отклонение: normalized_est_qty - spec_qty")
    
    # Float разрешен исключительно для secondary ranking/confidence scoring
    confidence_score: float = Field(..., ge=0.0, le=100.0)
    message: str

    @model_validator(mode="after")
    def compute_severity(self) -> "DiscrepancyReportItem":
        """Автоматическая эскалация критичности при системных ошибках размерности."""
        if self.collision_type in ("MULTIPLIER_ERROR", "INCOMPATIBLE_UNITS"):
            self.severity = "CRITICAL"
        return self
```

## 5. Алгоритмический конвейер сопоставления (Matcher Tuning)

### 5.1. Весовая формула подобия позиций
Итоговый показатель сходства строк $S_{\text{total}} \in [0.0; 100.0]$ вычисляется по каскадной формуле:

$$S_{\text{total}} = \mathbb{I}_{\text{unit}} \cdot \mathbb{I}_{\text{dim}} \cdot \left( w_1 \cdot S_{\text{code}} + w_2 \cdot S_{\text{fuzzy}} + w_3 \cdot S_{\text{context}} \right)$$

где:
* $\mathbb{I}_{\text{unit}} \in \{0, 1\}$ — блокирующий индикатор шлюза физических размерностей (Unit Gating). Равен $0$, если классы размерностей несовместимы.
* $\mathbb{I}_{\text{dim}} \in \{0, 1\}$ — блокирующий индикатор геометрических габаритов (Dimensional Filter). Равен $0$, если обнаружены несовпадающие диаметры/толщины.
* $S_{\text{code}} \in [0.0; 100.0]$ — точное соответствие шифров (100.0 при совпадении, 0.0 при отсутствии/несовпадении).
* $S_{\text{fuzzy}} \in [0.0; 100.0]$ — показатель текстового сходства, рассчитываемый алгоритмом `rapidfuzz.fuzz.token_sort_ratio`.
* $S_{\text{context}} \in [0.0; 100.0]$ — совпадение наименования раздела/подраздела (главы ССРС).

**Весовые коэффициенты:**

| Коэффициент | Значение | Обоснование |
| :--- | :--- | :--- |
| $w_1$ (Шифр/Код) | **0.45** | Наличие одинакового отраслевого кода (ФССЦ, ГОСТ, артикул производителя) — главный маркер идентичности. |
| $w_2$ (Fuzzy Title) | **0.40** | Очищенное текстовое наименование материала/работы. |
| $w_3$ (Контекст раздела) | **0.15** | Предотвращает ложный мэтчинг идентичных материалов из разных разделов (например, кабель в разделе ЭОМ vs кабель в разделе СС). |

**Пороговые значения (Thresholds):**
* `FUZZY_ACCEPTANCE_THRESHOLD = 85.0` — порог автосопоставления при отсутствии кода позиции.
* `FUZZY_SUSPECT_THRESHOLD = 70.0` — диапазон $[70.0; 84.9]$ направляется на ручную верификацию оператором в контрольном пункте SQLite. Ниже $70.0$ позиции признаются несовпадающими.

### 5.4. Правила фильтрации ложных срабатываний (False Positives)

* **Шлюз геометрических размерностей (Diameter/Thickness Lock):**  
  Если в строке спецификации выделен типоразмер (регулярные выражения: `(?:\b(?:d|ду|диам|ø)\s*[:=]?\s*(\d+)\b)`, `\b(?:толщ?|s)\s*[:=]?\s*(\d+)\b`), а в строке сметы присутствует иной числовой параметр размерности — значение $\mathbb{I}_{\text{dim}}$ принудительно устанавливается в $0$.  
  *Пример:* «Труба стальная Ду 50» и «Труба стальная Ду 500» имеют текстовую близость $>90\%$, но мгновенно отсекаются данным фильтром.
* **Шлюз классов размерностей (Unit Mismatch Disqualification):**  
  Прямой запрет на кросс-сравнение несовместимых групп. Строка спецификации в единицах `м2` (Площадь) ни при каких условиях не сопоставляется со строкой сметы в `м3` (Объем). Позиция маркируется статусом `INCOMPATIBLE_UNITS`.

## 6. Выявленные краевые случаи (Edge Cases)

| Краевой случай / Аномалия | В чем выражается физически | Способ программной обработки |
| :--- | :--- | :--- |
| **Топология `merged_cells` в Excel** | В сметных формах (421/пр) шапки разделов и наименования объединяются по колонкам $A \dots D$. При наивном чтении openpyxl дочерние ячейки содержат `None`. | Использование топологического генератора `extract_sheet_rows_unmerged`. До начала итерации строится карта объединенных областей, и значение левой верхней ячейки транслируется на весь виртуальный прямоугольник. |
| **Скрытый сдвиг кратности (Multiplier Shift)** | Сметчик взял расценку на 100 м², но внес объем напрямую из чертежа без деления на 100. Разница составляет ровно $100 \times$. | Детектор кратности: если отношение нормализованного объема к проектному попадает в коридоры $[9.8; 10.2]$, $[98.0; 102.0]$ или $[980.0; 1020.0]$, тип ошибки автоматически переопределяется как `MULTIPLIER_ERROR` со статусом `CRITICAL`. |
| **Автоматическая конвертация YAML в float** | Значения допусков (`rel_tol: 0.001`) при стандартном чтении `yaml.safe_load` парсятся как системный float, заражая вычисления погрешностью. | Все конфигурационные числовые параметры в `config.yaml` обязаны экранироваться кавычками (`abs_tol: "0.001"`). Загрузчик конфигурации выполняет валидацию и прямую инициализацию в `Decimal(str_val)`. |
| **Документальный разрыв «ВОР vs ЛСР» после экспертизы** | В ходе прохождения госэкспертизы сметчик срезает расценки в ЛСР под лимит, но не актуализирует исходную ведомость объемов (ВОР). | Внутренний кросс-чек файла: скрипт сверяет вкладки внутри одной книги Excel до сопоставления со спецификацией. При обнаружении расхождения между ВОР и ЛСР формируется флаг предварительного сметного брака. |
| **Задвоение неучтенных ресурсов (Embedded Materials)** | Материал (например, болты, электроды, клей) сидит внутри сметной расценки согласно ГЭСН, но подрядчик дополнительно выносит его отдельной строкой в ВОР. | Векторная проверка ресурсных частей расценок: если позиция расценки содержит ресурс $X$, а следующая строка вводит ресурс $X$ с признаком «по прайсу», строка маркируется как `DUPLICATE_RESOURCE`. |

## 7. Метрики эффективности конвейера (для ВКР и публикаций ВАК)

Для валидации эффективности на тестовой выборке реальных строительных объектов применяются следующие метрики:

1. **Метрики качества сопоставления (Matching Performance):**
   * $\text{Precision} = \frac{TP}{TP + FP}$ (доля корректно связанных пар «чертеж — смета»).
   * $\text{Recall} = \frac{TP}{TP + FN}$ (доля найденных связей от общего числа реальных пересечений).
   * $\text{F1-Score} = 2 \cdot \frac{\text{Precision} \cdot \text{Recall}}{\text{Precision} + \text{Recall}}$.
2. **Метрика выявления коллизий:**
   * **Collision Recall Rate (CRR):** Процент выявленных реальных сметных ошибок, подтвержденных независимой строительно-технической экспертизой.
3. **Экономический показатель (Budget Risk Value):**
   * Суммарный предотвращенный перерасход:
     $$\Delta B = \sum_{i \in \text{OVERRUN}} (V_{\text{est}, i} - V_{\text{spec}, i}) \cdot C_{\text{unit}, i} \quad [\text{вычисление строго в Decimal}]$$
